# 기술기준

## 1. 기본 기술 조건

- 프론트엔드: Next.js 16.x 기반으로 구성합니다.
- 백엔드/서버 런타임: Node.js 22 LTS 이상 기준으로 구성합니다.
- 가능하면 TypeScript를 사용합니다.
- TypeScript는 Next.js 16 및 Node.js 22 환경에서 안정적으로 검증된 5.4 이상을 사용합니다.
- Node.js 22 LTS 환경에서 안정적으로 동작하는 패키지를 우선 사용합니다.
- Node.js 22 LTS 및 Next.js 16 호환 범위를 벗어나는 문법, 런타임 API, 프레임워크 기능은 사용하지 않습니다.
- 실험적 기능, 카나리 문법, 최신 버전 전제 예제는 사용하지 않습니다.
- 패키지를 추가할 때는 Node.js 22 LTS 및 Next.js 16 호환성을 먼저 확인합니다.
- 구현은 App Router 기준으로 작성하고, Pages Router 또는 Edge Runtime 전제 예제는 임의 적용하지 않습니다.
- 호환성이 불명확하면 더 단순하고 검증된 방식으로 구현합니다.
- ESM 우선 구성을 사용하되, CommonJS 의존 패키지와의 호환성 문제를 반드시 검토하고 동적 import 또는 interop 설정을 명시적으로 처리합니다.

## 2. 환경변수 및 비밀값 규칙

- 환경 변수 기반 설정을 사용합니다.
- `.env.example`이 있으면 새 환경변수를 함께 반영합니다.
- 비밀값을 코드, 템플릿 예시, 테스트 fixture에 하드코딩하지 않습니다.

## 3. 런타임 및 패키지 주의사항

- Native addon(node-gyp) 의존 패키지는 Node.js 22 ABI 호환성을 먼저 확인합니다.
- OpenSSL 및 crypto 관련 deprecated API는 사용하지 않습니다.
- Jest, Vitest, ESLint, ts-node, Prisma, Sharp 등 런타임 민감 패키지는 Node.js 22 지원 버전으로 고정합니다.
- Edge Runtime와 Node Runtime API를 혼용하지 않습니다.
- `fs`, `child_process`, `worker_threads` 사용 시 서버 컴포넌트와 클라이언트 컴포넌트 경계를 명확히 구분합니다.

## 4. 구현 기본 원칙

- 타입 안정성을 우선합니다.
- 과도한 추상화보다 현재 요구사항에 맞는 단순하고 유지보수 가능한 구조를 우선합니다.
- 서버, 프론트, 공통 로직을 역할에 맞게 분리합니다.
- 문서에 없는 상태 전이, 예외 처리, 권한 규칙을 임의로 추가하지 않습니다.
