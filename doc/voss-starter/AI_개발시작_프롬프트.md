# VOSS 개발 원칙 프롬프트

## 문서 기준 정보

## 개요

이 문서는 VOSS 방식으로 새 AI 대화를 시작할 때 바로 붙여 넣을 수 있는 기본 프롬프트 원문입니다.

프로젝트에 포함된 스타터 번들 문서를 AI가 먼저 읽고, 문서 갱신과 구현과 검증을 한 흐름으로 이어 가도록 유도하는 것이 목적입니다.

```md

이 프로젝트는 즉흥 구현이 아니라, 문서를 기준으로 현재 상태를 갱신하면서 개발해야 합니다.

## 3. 문서 관리 규칙

- 기존 문서를 우선 갱신하고 같은 목적의 문서를 새로 중복 생성하지 마세요.
- 날짜별 복사 문서를 늘리지 말고 현재 기준 문서를 유지하세요.
- `doc/voss-starter` 아래는 VOSS가 관리하는 기본 문서 경로입니다.
- `doc/README.md`는 사용자가 읽는 작업 안내 문서이고, 루트 `README.md`는 저장소 기본 안내 문서입니다.
- 사용자 자유 문서가 필요하면 다른 경로를 새로 만들어도 되지만, 기본 문서의 역할을 대체하는 중복 문서는 만들지 마세요.
- 문서가 없는 상태에서 바로 구현부터 시작하지 마세요.

## 4. VOSS 공통 기술 기준

- 프론트엔드는 Next.js 16.x 기준으로 구성합니다.
- 서버 런타임은 Node.js 22 LTS 이상 기준으로 구성합니다.
- 가능하면 TypeScript를 사용합니다.
- TypeScript는 Next.js 16 및 Node.js 22 환경에서 안정적으로 검증된 5.4 이상을 사용합니다.
- Node.js 22 LTS 및 Next.js 16 호환 범위를 벗어나는 문법, 런타임 API, 프레임워크 기능은 사용하지 않습니다.
- 실험적 기능, 카나리 문법, 최신 버전 전제 예제는 사용하지 않습니다.
- 패키지를 추가할 때는 Node.js 22 LTS 및 Next.js 16 호환성을 먼저 확인합니다.
- App Router 기준으로 구현하고, Pages Router 또는 Edge Runtime 전제 예제는 임의 적용하지 않습니다.
- 호환성이 불명확하면 더 단순하고 검증된 방식으로 구현합니다.
- ESM 우선 구성을 사용하되, CommonJS 의존 패키지와의 호환성 문제를 반드시 검토합니다.
- 비밀값은 하드코딩하지 않고 환경변수로 다룹니다.
- `.env.example`이 있으면 새 환경변수를 함께 반영합니다.
- `fs`, `child_process`, `worker_threads` 사용 시 서버/클라이언트 경계를 명확히 구분합니다.

## 5. 저장 및 데이터 기준

- 소규모 프로젝트는 JSON 기반 로컬 저장을 허용할 수 있지만, 동시 접근과 무결성을 고려합니다.
- 지속 보관할 구조화 데이터는 PostgreSQL 사용을 우선 검토합니다.
- 중규모 이상 프로젝트는 VOSS 제공 PostgreSQL과 Prisma 사용을 우선 검토합니다.
- DB 접근은 Repository / Service 계층으로 분리합니다.
- UI 또는 Route에 직접 DB 호출 로직을 난립시키지 않습니다.
- 상태 전이와 저장 흐름은 문서와 구현이 일치해야 합니다.
- 데이터 모델을 만들기 전에 DB, 파일, 로그, 캐시, 큐, 검색 인덱스와 export에 영속 저장되는 필드를 목록화합니다.
- 개인과 연결된 종교·신념·건강·고유식별·고위험 금융정보 등 민감 필드는 저장 필요성을 먼저 줄이고, 불가피하면 AES-128 이상으로 필드 암호화합니다. 신규 구현은 AES-256-GCM을 우선합니다.
- 민감 필드의 정확 일치 검색이나 중복 확인이 필요하면 암호문과 별도로 전용 키를 사용하는 HMAC-SHA-256 검색값을 설계합니다.
- 암호화 키는 코드·Git·DB·암호문과 분리하고 VOSS 프로젝트 환경 설정에 비밀값으로 등록합니다. 키 원문은 문서, 로그와 점검 보고서에 기록하지 않습니다.
- PostgreSQL 사용이나 디스크 암호화만으로 민감 필드 암호화가 충족된다고 가정하지 않습니다. 저장 민감정보가 없으면 확인한 스키마와 저장 경로를 근거로 해당 없음 처리합니다.

## 6. 배포 및 환경변수 기준

- `.gitlab-ci.yml`은 서버 공통 관리 파일이므로 직접 수정 전제로 해결하지 마세요.
- `Dockerfile`과 `.dockerignore`는 저장소 최초 생성 시 권장 초기 파일로 제공되며, 이후에는 프로젝트 요구사항에 맞게 사용자가 관리합니다.
- VOSS의 기존 저장소 템플릿 동기화는 `Dockerfile`과 `.dockerignore`를 수정하거나 덮어쓰지 않습니다.
- 배포 문제가 있어도 먼저 애플리케이션 코드, 설정, 문서, 환경변수 설명으로 해결 가능한지 검토합니다.
- 새 환경변수가 필요하면 코드에 이름만 추가하고 끝내지 않습니다.
- 반드시 아래를 함께 정리합니다.
  - 필요한 환경변수 이름
  - 어디에 설정해야 하는지
  - 설정되지 않으면 어떤 문제가 발생하는지
- CI/CD를 깨뜨릴 수 있는 변경은 사전 검토 없이 진행하지 않습니다.

## 7. 구현 원칙

- 기능 단위로 작은 작업부터 진행합니다.
- 타입 안정성을 우선하고, 과도한 추상화는 피합니다.
- 서버, 프론트, 공통 로직을 분리합니다.
- 문서에 없는 상태 전이, 권한 규칙, 예외 처리를 임의로 추가하지 않습니다.

## 8. 검증 원칙

구현 후에는 가능한 범위에서 아래를 확인하세요.

- 프론트 빌드
- 서버 빌드
- 주요 사용자 흐름 또는 API
- 하네스/테스트
- 문서-구현 정합성
- 환경변수 안내 누락 여부
- 인증, 권한, 세션, 비밀값, 외부 API, 관리자 기능, AI/RAG 기능이 포함되면 배포 후 `doc/voss-starter/VOSS_AI통합보안점검.md`와 `doc/voss-starter/tools/security_scan.py`를 사용합니다.
- 통합 문서에 포함된 기준으로 AI 점검, 원본 보고서 생성, VOSS 제출을 이어서 진행합니다.
- 배포된 운영 버전에 대해 공식 점검 이력을 남길 때는 먼저 통합 문서와 스캐너로 점검과 보고서 생성을 끝냅니다. 이후 VOSS의 `배포/운영 관리 > 보안 점검` 탭에서 30분 제출 토큰과 제출 정보를 발급받아 같은 AI에게 전달하고 VOSS 제출 API까지 호출합니다.
```

## 작업 시작 규칙

1. 먼저 위 문서를 읽고 현재 문서 구조를 요약합니다.
2. 구현 전에 어떤 문서를 갱신해야 하는지 먼저 적습니다.
3. 구현 후 하네스와 정합성 점검을 먼저 마칩니다.
4. 배포가 끝나면 통합 보안 점검 문서로 현재 운영 버전 AI 점검과 결과 정리를 수행합니다.
5. 운영 버전 점검 이력이 필요하면 점검 결과를 확정한 뒤 VOSS의 `배포/운영 관리 > 보안 점검` 탭에서 제출 토큰을 발급해 바로 VOSS 제출 API까지 완료합니다.
